# Clinic Scheduling Agent

A small, tool-using appointment scheduler with a deterministic evaluation and policy-improvement loop. Appointment side effects are owned by SQLite-backed tools; the model only proposes tool calls and patient-facing text.

## Setup

```bash
python3 -m venv .venv
.venv/bin/pip install .
```

For a live conversation, configure `OPENAI_API_KEY` and `OPENAI_MODEL`. Set `OPENAI_BASE_URL` when using an OpenAI-compatible endpoint other than the default.

## Run the agent

```bash
.venv/bin/scheduler-agent --model "$OPENAI_MODEL"
```

The CLI uses a trusted local demo identity (`demo-patient` by default), seeds sample availability into `data/scheduler.db`, and writes a completed JSON trace under `artifacts/traces/`. Type `exit` to finish and save the trace.

## Run evaluation and improvement

```bash
.venv/bin/scheduler-eval
```

This command runs the same 10 scripted scenarios against policy v1 and a candidate v2, writes traces and an improvement report under `artifacts/evaluation/`, and persists v2 only when the target scenario improves without regressing a previously passing scenario. The offline proposal is generated by a deterministic fake model so the command is repeatable. To use a live model for the structured proposal, set `OPENAI_API_KEY` and `OPENAI_MODEL`, then run:

```bash
.venv/bin/scheduler-eval --live-proposer
```

The scenario runner still uses scripted responses. The ambiguous-selection fake activates its v2 response only when the candidate prompt contains the validated ambiguity/clarification/no-guess rule. This simulates policy following for a repeatable regression demonstration; it does not measure an LLM’s general language understanding. The live CLI provides the open-ended conversation.

## Recording walkthrough

For the submission recording, show a short booking conversation in the CLI, exit so its trace is saved, then run `.venv/bin/scheduler-eval --live-proposer` with model credentials configured. Open `artifacts/evaluation/improvement-report.json` and show the failed v1 case, structured proposal, accepted v2 policy, 90% → 100% score, and empty protected-regression list. The evaluation’s scenario responses are scripted even when the proposal comes from the live model; call that out in the recording.

## Architecture and evaluation

The runtime flow is:

```text
Patient turn → ConversationRun → ModelClient → validated tool dispatcher → SQLite
                    └──────────── JSON trace ─────────────────────────────┘
```

Active conversation state stays in memory for the process. SQLite is authoritative for appointments. The tool dispatcher gets patient identity from trusted CLI/session context; identity is excluded from model-facing arguments and appointment tool results.

The rubric checks active/cancelled appointment state, required and forbidden tool calls, expected tool errors, and required response terms. Each scenario passes only when all checks pass; the aggregate score is the passing scenario percentage. The evaluator is deterministic. There is no LLM judge in this version: the scripted fixtures have explicit assertions, and a transcript-only judge cannot verify whether a booking exists in SQLite or whether a tool call succeeded. A judge could later score conversational clarity, but it must not decide booking correctness or safety.

The improvement demo targets an ambiguous “that one” reference. The v1 fixture books the first slot and fails. A structured proposal adds a clarification rule. The v2 fixture asks which slot the patient means and passes. Promotion requires the target to pass and every scenario that passed under v1 to remain passing. The report identifies the scripted proposer; use of the fake is part of the demo limitation, not evidence that a live LLM improved by itself.

For the interactive CLI, `--patient-id` is trusted local application context, not authentication. The demo uses synthetic patients and appointments; a deployed clinic system would need a real authenticated identity provider and appropriate data protections.
