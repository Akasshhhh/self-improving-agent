# Design note

This take-home keeps the probabilistic model outside the authoritative scheduling boundary. The model can ask to search, book, list, or cancel; Pydantic validates its arguments and the dispatcher supplies the trusted session patient identity. A first booking request stages an offered slot and displays a fixed confirmation prompt; only a later patient confirmation authorizes the dispatcher to book that same slot. SQLite rechecks availability inside a transaction, and a unique active-slot index prevents double booking. A model response saying “confirmed” is not evidence of a booking.

Conversation state is in memory for one CLI process. Appointment state is durable in SQLite. Each run produces a JSON trace with policy/agent versions, messages, tool calls and arguments, tool results/errors, and final appointment state. This separation makes traces useful for evaluation without allowing them to become a second source of truth. Redis was omitted because the single-process demo does not need shared session state; a multi-worker service could use Redis for short-lived active context while retaining durable records in a database.

Evaluation checks database outcomes, attempted tool calls, and successful tool results. A case passes only if every check passes; the aggregate is the case pass percentage. The offline scripted suite demonstrates the ambiguous “that one” case improving from v1 to v2; its simulated model responses make that result repeatable. The live CLI uses an OpenAI-compatible model, then reviews the saved trace and can generate a synthetic scenario and proposal. Admin approval runs the real model against frozen target and protected scenarios before promotion.

The live gate uses a narrow model judge only for an optional conversational response goal. A transcript-only judge cannot inspect SQLite or verify tool side effects; deterministic checks remain responsible for safety and booking correctness.

Known replay limit: generated rescheduling scenarios currently require the source trace to begin with this patient's booked appointment. This keeps the proposed test tied to observed evidence, but a booking made earlier in the same chat is absent from that starting snapshot. Later, capture bounded appointment state immediately before the failed request (or reconstruct it from ordered successful tool events) and validate against that state. Simply removing the evidence check would allow a generated test to invent a pre-existing appointment.

AI tools helped scaffold and implement the repository. Engineering judgment overrode generated breadth in favor of a small SQLite-backed design, trusted session identity, deterministic acceptance gates, and a disclosure that scripted before/after behavior is simulated. The demo assumes synthetic patient data and a trusted local CLI identity; it is not a production authentication or privacy design.
